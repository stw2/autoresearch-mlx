## Assertion

Within the current training loop, the best reachable `TOTAL_BATCH_SIZE` is the minimum valid value, `2**15`. It improved `val_bpb` substantially over the `2**16` baseline, and every larger valid batch I tested (`2**17` through `2**19`) degraded monotonically while peak memory stayed flat.

## Conditions

- 5-minute training budget from `prepare.py`
- Apple Silicon MLX training stack in the repository default setup
- Depth fixed at `4` with the baseline architecture and optimizer hyperparameters unchanged
- `DEVICE_BATCH_SIZE=16`, `MAX_SEQ_LEN=2048`, so valid `TOTAL_BATCH_SIZE` values must be multiples of `32768`
- Peak memory remained effectively constant at about `21.2 GB` across all successful runs

## Falsification

I first tried to disprove the "sweet spot at `2**15`" claim by going smaller to `2**14`, but that configuration is not legal in this implementation because `TOTAL_BATCH_SIZE % (DEVICE_BATCH_SIZE * MAX_SEQ_LEN) == 0` must hold. I then used larger valid batches as the operational falsification path: if `2**15` were only a lucky run, `2**17` or above should have matched it, but instead `val_bpb` worsened sharply and monotonically as batch size increased.

## Implications

The current setup is strongly update-frequency limited under the 5-minute budget. Follow-up work should treat `2**15` as the batch-size anchor and look for gains elsewhere, or explicitly modify `DEVICE_BATCH_SIZE` if we want to explore even smaller effective total batches without violating the current divisibility constraint.
