## Assertion

After reducing `TOTAL_BATCH_SIZE` to `2**15`, the earlier shallow-depth result still holds and sharpens into a local optimum at `DEPTH=2`. Both neighboring depths I tested were worse: `DEPTH=1` regressed substantially, and `DEPTH=3` was closer but still worse than `DEPTH=2`.

## Conditions

- 5-minute training budget from `prepare.py`
- Apple Silicon MLX training stack in the repository default setup
- `TOTAL_BATCH_SIZE=2**15`, `DEVICE_BATCH_SIZE=16`, `ASPECT_RATIO=64`, `HEAD_DIM=128`, AdamW hyperparameters unchanged

## Falsification

The explicit falsification run was `DEPTH=2` from the `TOTAL_BATCH_SIZE=2**15` control. If the smaller batch had removed or reversed the earlier shallow-depth advantage, this run should have matched or lost to `DEPTH=4`; instead it improved `val_bpb` by `0.050069`, reduced peak memory from `21.2 GB` to `18.6 GB`, and more than doubled the number of optimizer steps completed in the budget (`2214` vs `909`).

## Implications

The best-known configuration now combines both published directions: use the minimum legal total batch and keep depth near 2, not 4. Follow-up work should tune within the shallow regime around this new anchor commit, because the result is no longer just "smaller is better" in general: `DEPTH=1` over-shoots the optimum and loses badly.
