## Assertion

At the current best shallow anchor, reducing `DEVICE_BATCH_SIZE` from `16` to `8` did not improve `val_bpb` at any tested valid `TOTAL_BATCH_SIZE`. The direct attempt to unlock the smaller global batch `2**14` regressed sharply, and even the same-total-batch isolation run at `2**15` still failed to beat the control rerun.

## Falsification

The explicit falsification run halved `DEVICE_BATCH_SIZE` to `8` and used the newly legal minimum `TOTAL_BATCH_SIZE=2**14`. If the previous shallow anchor were limited mainly by update frequency, this run should have improved on the control. Instead it regressed by `0.022592 bpb` while leaving peak memory essentially unchanged, so the core hypothesis failed immediately.

## Implications

For the current depth-2, 128-d shallow regime, the winning setting remains `DEVICE_BATCH_SIZE=16` with `TOTAL_BATCH_SIZE=2**15`. Follow-up work should look elsewhere for gains rather than pushing microbatching smaller, unless another architectural change materially alters throughput or memory behavior.
